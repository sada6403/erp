# POS ERP 2.10.0 (2026-11-24)

Desktop 2.10.0; cloud, superadmin portal and native mobile source 1.1.0. This is a local release candidate, not a production deployment.

## Behavior

Email remains available. Users can sign in with their case-insensitive User ID or email. Admins can choose IDs and passwords for cashiers; duplicate IDs show a clear error. Existing email local parts generate IDs with numeric suffixes. Passwords remain bcrypt hashes, and visibility controls start hidden. Remembering stores only the identifier. Existing role, branch, PIN, lockout and management restrictions remain enforced.

The native customer/agent app has a separate app_users account system. Existing phone/member/agent IDs remain supported; email is accepted when it identifies exactly one active app account. It does not grant desktop cashier permissions to customer accounts.

Duplicate physical batches show existing quantity and entry date before Add quantity or Cancel. Different dates and expired entries require confirmation. Manufacture/expiry order is enforced in the database write path. A unique (product_id, batch_no, expiry_date) key lives in product_batch_identities. Receipt rows remain separate to preserve cost valuation; they reference that physical identity. The batch screen totals physical quantities per branch and retains receipt costs.

## Migration: isolated copies first

Do not point staging runners at a live company database. Back up application data and test a restored copy. Review case-insensitive duplicate emails first; the migration stops instead of choosing an account to overwrite.

SQLite, from the repository root (after compiling Electron):

```powershell
npx.cmd tsc -p tsconfig.electron.json
$env:ELECTRON_RUN_AS_NODE='1'
.\node_modules\electron\dist\electron.exe scripts/migrate-release-2.10.cjs --staging-copy --db C:\staging\company.db --backup-dir C:\staging\backups
```

The desktop also runs the same backup-first, transactional migration on workspace initialization. SQLite backup integrity is checked before schema changes. Existing emails, password hashes, stock quantities and receipt costs are retained. Review generated User IDs in Users. Review physical identities with needs_review=1 before adding to those legacy batches; conflicting manufacture dates require human reconciliation without deleting receipts.

Cloud, from backend (use staging connection environment already configured; never place secret values in logs):

```powershell
$env:RELEASE_ENV='staging'
$env:RELEASE_DATABASE='isolated_tenant_copy'
$env:RELEASE_BACKUP_DIR='C:\staging\mysql-backups'
node scripts/migrate-release-2.10.mjs up
```

mysqldump must be installed. The runner aborts if the backup fails. For the platform superadmin database, set its staging database name and append --platform. Run the release migration explicitly before enabling the new cloud login/reset features; older schemas retain email login fallback. MySQL DDL is not transactional: on failure retain the backup, fix the reported issue and rerun the idempotent staging runner.

Configure PUBLIC_APP_URL (HTTPS), or NEXT_PUBLIC_APP_URL, and the company's existing SMTP settings for email reset links. Reset links expire in 15 minutes, store only token hashes, and become invalid after use or a password change. Offline installations retain admin reset and their existing local recovery flow.

## Rollback

Run the same SQLite command with --down, or the cloud runner with down (and --platform for platform DB). Each runner backs up first. Compatibility rollback removes new user uniqueness indexes while retaining additive IDs, batch identities, links, quantities and password hashes. Reinstall the preceding application only after testing its compatibility on the restored staging copy. To undo all migration data changes, restore the verified pre-release backup with applications stopped. Never restore an old backup over newer sales without reconciliation.

## Release checks

Record final test/build outcomes alongside this document. SMTP delivery, real MySQL staging migration, native emulator checks and two-device sync need the appropriate test services/devices. A successful compile alone does not establish these outcomes. Release migration runners were not executed against a company database. No remote push, email send or deployment was performed. The first cloud build invoked its pre-existing database auto-migration code against the configured connection (duplicate-column/deadlock warnings); the build command now explicitly disables those automatic migrations, and the subsequent build completed with no autoMigrate output. This is not a validation of cloud migration or its earlier side effects.


Verified locally:

- Desktop TypeScript and Electron compilation pass.
- Desktop unit suite: 306 passed; the subsequent focused login suite passed both tests, including the newly added email-link recovery regression.
- Local integration suites: 337 passed, 23 skipped, across the large SmartBuy/security/sync runs and 20 remaining files. Live-server app API suites were stopped because no seeded test API service was supplied; they are not counted as passing.
- Native mobile TypeScript, lint and 93 tests pass. No connected emulator/device was available. Mobile APK/AAB was not built; native source version is 1.1.0 (staging 1.1.0-rc.1, production versionCode 8 reserved locally).
- Cloud production build and superadmin portal build pass.
- Electron SQLite ABI smoke check passes against an in-memory database. Local NSIS packaging uses that already-verified binary with npmRebuild=false; the first normal packaging attempt could not replace it while tests held it open.
- Existing legacy SmartBuy QA finding messages and missing credit_ledger fixture warnings remain in the logs despite passing assertions; this release does not claim to resolve them.

Pending before production rollout: run the backup-first MySQL migration on an isolated tenant/platform copy (mysqldump is not installed here); verify company SMTP reset delivery, token redemption through the deployed API, cross-device batch sync and native screens on a device. Use the generated installer only for staging acceptance until these checks are complete.
