## 2026-11-12 Step 6 start: join requests and bank slips (Moni's decisions)
- **One shared join-request flow.** Agent-initiated Smart Buy join (v1.0) and customer self join (later) use the same table `smartbuy_join_requests`, the same endpoint `POST /smartbuy/join-requests` (multipart, idempotent on `client_event_id`) and the same POS review. `source` is `agent` when the caller has the agent role, else `self` (the customer's own `customer_id` is stored). The API accepts both roles now; only the agent screen exists in the app for v1.0.
- **NIC photos and bank slips are private files.** Stored by `lib/app/privateFiles.ts` in `PRIVATE_UPLOAD_DIR` (default `<cwd>/private-uploads`), never under `UPLOAD_DIR` (which `/api/files` serves). Validated by magic bytes, max 6 MB, EXIF stripped, re-encoded to WebP 1600 px. Only the admin routes (POS key) stream them, `Cache-Control: private, no-store`.
- **Approval creates the member in the cloud, atomically** (`decideJoinRequest`): customer (matched by phone) + `chit_members` row with the next `join_order`, the submitting agent's `agent_id` (the agent keeps the credit), capacity = `max_customers || member_count`, registration window, pending scheme activates at `min_members`. Customer + member then sync down to the POS like any other cloud row.
- **Cloud `customers` has no NIC / branch / notes columns** (POS-only). So the NIC is kept on the request row, shown in the POS App Requests screen, and written into the local POS customer by the POS (`fillLocalNic`, only fills an empty NIC). Not widening the cloud customer schema without a decision (it would start storing every customer's NIC in the cloud).
- **Duplicate rules:** same phone (or NIC) with a pending request for the scheme -> 409; already a member (phone match) -> `ALREADY_MEMBER`; scheme full counting pending requests -> `SCHEME_FULL`.
- **Bank slips:** one slip waits at a time per order; a rejected slip can be replaced (max 5); verify sets `payment_status='paid'`, `paid_amount=total`; the customer is notified. COD orders and cancelled/paid orders refuse slips.
- **POS screen:** Mobile App > App Requests (Super Admin only, like App Access): Join Requests and Bank Slips tabs, photo viewer, approve/reject with reason, audit log rows (`APP_JOIN_*`, `APP_SLIP_*`).
- **Dev test note:** local dev runs without `SYNC_PULL_OVERLAP_MINUTES`; an order created in the same DB second as the previous pull cursor is skipped by the strict `updated_at > cursor`. Production sets the overlap (runbook 3a), so only the dev integration tests needed a 1.1 s pause (SHOP-04, SHOP-12).

## 2026-11-12 NIC privacy and retention (Moni)
- **NIC never goes into the cloud `customers` table** (privacy). Cloud customers has no NIC column and none will be added; a test (JOIN-05) asserts it. This replaces the earlier "POS writes NIC via fillLocalNic on list" wording: at approval time the POS remembers `{customer_id: nic}` (persisted `pending_member_nic`) and writes the NIC into the local POS customer once that row has synced down (retries at 35 s / 70 s / 130 s and whenever App Requests opens). The approved NIC therefore lives only in the POS customer record.
- **Retention: NIC number and both NIC photos on a join request are deleted 30 days after the approval or rejection.** `purgeJoinRetention` blanks `nic_number`, clears the photo refs, deletes the private files and sets `purged_at`; name, phone, scheme and decision stay so the history is readable. Pending requests are never purged. No scheduler: it runs lazily when the POS opens the list and (at most every 10 min) when a join request is submitted. If a scheduler is added later it can call the same function.
- Bank slip images are not NIC data; they are kept (payment proof) until a retention period is decided.
- **Backup check (2026-11-12):** the earlier 408 KB dump was correct (the production MySQL data really is ~12k rows, 1-6 MB per database). Redone per database (`--single-transaction --routines --triggers --events`), each restored into a scratch DB and compared by exact row count and `CHECKSUM TABLE`: all 6 identical, scratch DBs dropped. Gap found: PostgreSQL (`nature_farming`) and MongoDB (`nf-farming` 235 MB, `nf-plantation`, `nf_farming`, `nf_plantation`) belong to other apps on the same server and are in no backup.
